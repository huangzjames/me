写给人看的页面：一篇样式完整的备忘

很多产品文档写得像说明书，很多个人文章又写得像日记。真正耐读的长文，往往介于两者之间：有结构，但不僵硬；有观点，但不喊口号；有细节，但不把读者淹没在格式里。

这篇文字不是为了教你 Markdown 语法，而是借一个真实话题——怎样把复杂想法写进网页——把博客详情页常见的视觉元素都走一遍。如果你正在检查文章页或项目页的渲染效果，可以直接从这里开始对照。

先定读者，再定结构

我写文章时通常会先问三个问题：

  1. 读者是谁 — 同事、客户，还是未来的自己？
  2. 他读完要带走什么 — 一个判断、一张清单，还是一段可引用的表述？
  3. 他会在哪里打断 — 手机、地铁、会议前五分钟？

这三个问题听起来很「咨询腔」，但它们会直接影响排版选择。比如：

  • 需要快速扫读的人，会更依赖 小标题 和 表格；
  • 需要跟着做的人，会更依赖 有序清单 和 代码块；
  • 需要被说服的人，会更依赖 引用 和 强调框。

标题层级：让读者始终知道「我在哪一层」

网页里的标题，不只是字号变化，而是 信息地图。

二级标题：一个完整观点

二级标题应该能单独成立。比如这一节的观点是：标题层级要服务于理解，而不是装饰。

三级标题：一个可执行的子块

三级标题适合放方法、例子、反例。再往下就不建议堆太多层级了——网页不是论文目录，读者不会为了找第 4.2.3 节而耐心翻页。

正文里的基础样式

普通段落用 serif 字体，链接会回到 文章列表，也可以跳到外部参考，例如 Markdown Guide。如果你更习惯裸链接，也可以直接写 https://astro.build。

强调有几种常见写法：

  • 加粗 用来标记结论；
  • 斜体 用来标记语气或不确定；
  • 加粗加斜体 只留给真的很关键的句子；
  • 删除线 表示已经放弃的旧想法；
  • inline code 表示文件名、命令或短代码片段；
  • 高亮 适合临时提醒；
  • H2O 这样的下标、E=mc2 这样的上标，以及 API 这类缩写说明，都可以混在正文里。

快捷键示例：⌘ + S 保存，⌘ + Shift + P 打开命令面板。

列表：无序、有序，以及嵌套

无序清单

写网页内容时，我常会先列一个「不要做什么」：

  • 不要一屏只有一句话
  • 不要连续三个段落都不分段
  • 不要把表格当 Excel 直接贴上来
    • 列太多时，考虑拆成两段
    • 或者改成列表
  • 不要忘记给图片写说明

有序清单

如果读者需要按步骤执行，就用数字：

  1. 先写结论，再补论据
  2. 每个二级标题下至少有一个完整段落
  3. 需要对照的数据放进表格
  4. 需要复用的命令放进代码框
  5. 发布前在手机上看一遍

任务清单

发布前的最后一轮检查：

  • 标题是否只表达一个主题
  • 图片是否有 alt 和说明
  • 表格是否在窄屏可横向滚动
  • 代码块是否标注语言

引用：把别人的话和自己的判断分开

好的写作不是把全部思考过程写出来，而是把 思考的结果 写清楚，同时保留足够线索，让读者知道你是如何到达这里的。

—— 这句是我编的，但很像我在改稿时会提醒自己的话。

引用块适合放：原话、反例、需要被单独看见的判断。不要整篇都用引用，否则页面会像聊天记录。

居中的一句话总结：引用负责「停一下」，正文负责「继续走」。

左对齐段落继续往下写。大多数正文都应该保持默认左对齐，这样在手机上也最自然。

右对齐更适合署名、日期或一句收束。—— 2026.05

表格：把对照关系写清楚

下面这张表不是业务数据，而是 段落类型 与 适用场景 的对照。注意表头左对齐、数字列右对齐的写法：

元素适合做什么不适合做什么优先级
段落展开论证堆参数1
小标题切分结构代替段落2
表格横向比较讲故事3
代码块可复制步骤写长段观点4
配图建立直觉替代文字5

表格行数不必多，三到五行 往往最耐看。列太多时，详情页会自动允许横向滚动，这正是我们需要测试的行为之一。

代码块：给「可复用」的内容

Inline code 适合 package.json、astro.config.mjs 这种短名字。整段命令或脚本，则应该放进代码框：

function estimateReadingBlocks(paragraphs) {
  return paragraphs.filter(Boolean).map((text, index) => ({
    id: index + 1,
    kind: text.startsWith("#") ? "heading" : "body",
    length: text.length,
  }));
}

console.log(estimateReadingBlocks([
  "## 示例",
  "这是一段用于测试代码高亮的正文。",
]));

如果需要终端命令，也可以单独放一段：

pnpm dev
# 本地打开文章详情页，检查 prose 样式

强调框：把「请注意」从正文里拎出来

模板没有单独的 Callout 组件时，我会用一个小型 aside 来放 提醒、结论或反常识判断：

✅ 小结

如果一篇文章需要读者记住一件事，那就把这件事写进一个小框里。不要指望读者从八段文字里自己提炼。

这类框不宜太多。一篇长文里 一到两个 就足够。

配图：放在段落之间，而不是段落中间

第二张图放在后半段，用来表达「结构」而不是「情绪」。好的配图应该让读者看完文字后，更快理解关系，而不是打断阅读节奏。

图片说明（figcaption）很重要。它不负责重复 alt 文本，而是告诉读者 这张图在论证什么。

脚注、分割线与空白

有些补充信息不适合放进正文，比如术语来源、延伸阅读。可以用脚注 1，再在文末统一解释 2。

Emoji、链接与最后检查

Emoji 可以用，但别让它替代信息。✨ 适合表达情绪，📌 适合标记重点，⚠️ 适合提醒。若整段都是 Emoji，读者会以为你在发群聊。

最后再列几个容易忽略的渲染点：

  1. 超链接 是否可点、hover 是否正常
  2. 加粗 在深色模式下是否仍然清晰
  3. 表格 是否不会把页面撑破
  4. 代码块 是否能在窄屏横向滚动
  5. 图片 是否居中、是否不会溢出

结语

如果这篇「样式备忘」读起来仍然像一篇正常文章，而不是测试清单，那说明排版是 为内容服务 的。反过来，如果某一类元素看起来特别突兀——比如表格太宽、引用太亮、代码框太挤——那就回到 global.css 和 prose 配置里微调。

你可以把这篇当作 文章详情页 的基准样张；项目详情页若也需要同样效果，把正文结构复制过去即可。欢迎边读边对照：哪些地方顺眼，哪些地方还需要改。

Happy writing. 🌿
